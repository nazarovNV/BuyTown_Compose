# Архитектура BuyTown

Приложение использует MVVM и однонаправленный поток данных:

`действие пользователя → ViewModel → Repository → UiState → Compose`

## Структура

- `domain/model` — модели товара, пользователя, профиля и позиции корзины. Без Android и Compose.
- `domain/repository` — контракты авторизации, товаров, корзины и профиля.
- `data/source` — локальное хранилище аккаунтов и демонстрационные товары.
- `data/repository` — реализации контрактов. Работа с диском и хеширование выполняются на `Dispatchers.IO`.
- `di/AppContainer` — создание зависимостей с временем жизни приложения. Контейнер доступен только в точках сборки интерфейса (`Route`).
- `presentation/auth` — форма входа/регистрации, её состояние и ViewModel.
- `presentation/shop` — оболочка с вкладками, типизированные направления и стек переходов.
- `presentation/catalog` — главная с поиском, категории, сетка и подробная карточка.
- `presentation/cart` — состояние, ViewModel и экран корзины.
- `presentation/profile` — состояние, ViewModel и экран профиля.
- `presentation/common` — общие элементы интерфейса, форматирование цены и сопоставление иллюстраций.
- `presentation/navigation` — корневая точка маршрутизации по состоянию сессии.
- `presentation/theme` — оформление Material 3.

## Правила изменений

1. `Screen` получает неизменяемое состояние и обработчики действий. Он не читает Preferences, не создаёт репозитории и не сохраняет данные.
2. `ViewModel` предоставляет read-only `StateFlow<UiState>`, валидирует действия и вызывает интерфейсы репозиториев. `Context` и Compose в ViewModel не используются.
3. `Route` создаёт ViewModel через фабрики, собирает Flow через `collectAsStateWithLifecycle` и связывает обработчики с экраном.
4. Реализации хранилищ подключаются в `AppContainer`. Для перехода на сервер или БД заменяется реализация контракта, а не экран.
5. Общие компоненты, включая счётчик корзины, остаются в `presentation/common`.
6. Простой вызов репозитория выполняется из ViewModel. Отдельный use case следует вводить для переиспользуемого сценария, объединяющего несколько репозиториев.

Пока это один Gradle-модуль с разделением по слоям и функциональным областям. При росте команды `domain`, `data` и функциональные области можно выделять в Gradle-модули. Добавлять пустые модули и интерфейсы без отдельной ответственности не требуется.

## Время жизни состояния

- Корневые ViewModel живут в Activity и переживают смену конфигурации.
- `AppViewModel` владеет `ViewModelStore` авторизованной сессии. ViewModel магазина, корзины и профиля переживают поворот экрана и очищаются при выходе. Повторный вход начинает навигацию с главной.
- Пароли формы находятся только в памяти; в SavedState/Bundle они не записываются.
- Аккаунты сохраняются в прежнем файле `local_accounts`, поэтому существующая регистрация совместима. Хранятся соль и PBKDF2-хеш, а не открытый пароль.
- Профиль сохраняется отдельно для каждого логина. Старый профиль demo читается как начальное значение.
- Корзины разделены по логинам и хранятся в памяти процесса, без сохранения после принудительной остановки приложения.
- После уничтожения процесса приложение снова показывает вход. Постоянной серверной сессии и оформления заказа в демо нет.

## Проверки

```powershell
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest
.\gradlew.bat :app:connectedDebugAndroidTest
```

Модульные тесты проверяют поиск, навигацию, границы количества, сумму и изоляцию корзин. Инструментальные тесты проверяют сохранение аккаунта, валидацию формы и профиля, а также сценарий через реальный Compose-интерфейс с поворотом экрана.

Для локального входа остаётся аккаунт `demo / demo123`. Можно зарегистрировать собственный аккаунт.
